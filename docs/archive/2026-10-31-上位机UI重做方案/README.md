## 当前问题与基线

源码检查及浏览器截图表明：

1. 两页使用 17px 基础字号、52px 常规按钮、24px 大圆角，卡片和提示多层叠加；建图首屏用于标题、流程、启动提示的空间偏多。
2. 强调色、阴影、圆角和分区数量让多个区域同时争夺注意力，主要任务与辅助信息的层级不够明确。这是本轮设计判断，不是性能测量结论。
3. 两页有可沿用的地图绘制、状态反馈、触屏控制和浏览器回归，UI 重做应保留这些功能契约。
4. 巡检是 Vue 3.5.44／Vite 8.3.4；建图是本地 HTML／CSS／JavaScript。无需为此次视觉改版迁移到 React、引入完整 UI 库或改变 ROS 2 Humble 后端。
5. 根工作区有大量未提交修改。普通 8080 按交接运行 `/home/jetson/luhao/my_nav_carcar_return_nearby_release` 冻结发布，包含恢复、附近返程和手机启动布局修复。正式改版前必须逐项核对发布页与根源码差异，不能用旧工作区网页整体覆盖发布版。

## 参考项目与取舍

### Linear：视觉结构的主要参考

[官方 UI 重设计说明](https://linear.app/now/how-we-redesigned-the-linear-ui) 讨论侧栏、页头、面板的对齐、导航密度和减少视觉噪声，并强调限制重设计范围。

采用：安静的导航区域、明确的页头、连续工作区、克制的层次和一致的组件尺度。适配：中文文字长度、较大的触屏点击区域、常驻停车与现场状态。Linear 是商业产品，本文作为设计方法参考，不复制其资源或源码。

### Open-RMF Web：机器人任务和地图交互参考

已阅读 [README](https://github.com/open-rmf/rmf-web)、[地图图层控制实现](https://github.com/open-rmf/rmf-web/blob/main/packages/rmf-dashboard-framework/src/components/map/layers-controller.tsx)、[对应交互测试](https://github.com/open-rmf/rmf-web/blob/main/packages/rmf-dashboard-framework/src/components/map/layers-controller.test.tsx)、[框架依赖](https://github.com/open-rmf/rmf-web/blob/main/packages/rmf-dashboard-framework/package.json) 和主题接口。

采用：地图作为主工作面，图层、缩放与全图工具放在地图上下文中，任务与设备信息相邻。源码中的图层菜单使用悬停展开；本项目需要点击／触摸／键盘可用的展开方式，不能原样照搬。

该仓库为 Apache-2.0，查询时未归档、最近推送为 2026-10-30；存在 CI、组件测试和 Storybook。当前 README 主线支持环境已到 Ubuntu 26.04／ROS 2 Lyrical，框架依赖 React、MUI、Three 等。它与本项目 Vue／原生网页及 Humble 的直接集成成本较高，因此只借鉴布局和交互，不引入 RMF 后端或前端框架。近期提交和测试存在不等于已验证其工业可靠性。

### IBM Carbon：状态与故障反馈参考

已阅读 [通知设计规范](https://www.carbondesignsystem.com/building-blocks/core/components/notification/guidelines) 和 [Notification 实现](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/Notification/Notification.tsx)。其内联、短时、可操作通知区分适合本项目不同故障层级。

采用：重要故障紧邻任务长期保留，带原因与恢复动作；成功提示轻量表达；颜色与文字／图标同时表达状态。代码中键盘关闭、焦点范围和事件监听清理是后续组件实现的参考。Carbon 为 Apache-2.0，查询时未归档、最近推送为 2026-10-30。其 React 组件不直接接入本项目，避免额外运行依赖。

### Foxglove：辅助参考

阅读了 [官方布局文档](https://docs.foxglove.dev/docs/visualization/layouts) 和 [当前 Studio 仓库说明](https://github.com/foxglove/studio)。借鉴按任务组织地图、图像和诊断面板的思路。当前仓库说明主要指向产品下载和文档，本轮不把它作为可直接移植的开源 UI 实现，不引入商业嵌入或复杂自由拖拽布局。

以上成熟设计可减少重新探索信息分区、通知语义和交互基本规则的工作。仍需自行完成两页样式、现有 DOM／Vue 模板适配与真实状态回归；不存在可以直接替换本项目控制台而保持全部接口的现成皮肤。

## 推荐实现方案

### 视觉规范

背景 `#F5F6F8`，工作面 `#FFFFFF`，正文 `#252C36`，辅助文字 `#687380`，边界 `#E1E5EB`，主操作 `#285BD4`。红色保留给停车／危险状态，绿色保留给已确认正常状态；以上为界面色，地图图层原有颜色含义单独保留。

采用本机中文无衬线字体，避免外部字体请求。页标题约 24～26px，正文 14～15px，辅助信息 12～13px；关键数值使用等宽数字。正式实现需在目标平板检查可读性，不把缩小字号当作唯一的紧凑方式。

常规控件圆角约 6px，工作区约 9px，以细边界组织空间。桌面普通操作约 36～40px；触屏主要操作至少 44px。主操作突出，次要操作平实，详细信息按需展开。减少重复卡片、同等级标题和大面积装饰阴影。

### 信息布局与状态

- 桌面：左导航＋顶部状态／停车＋中央地图＋右侧任务面板。
- 平板：缩窄导航和面板，保持主要按钮可直接触达。
- 手机：导航压缩为顶部入口，地图与任务纵向排列，停车随滚动保持可见；正式实现进一步核验当前阶段关键操作的触达距离。
- 建图待命：右侧显示新建／续建和控制方式，主操作清楚说明会检查并启动硬件；没有数据时解释下一步。
- 建图运行／暂停／故障：右侧按真实状态显示暂停、继续、返程、恢复、接管；不能把不同恢复条件简化为同一个“继续”。
- 保存／审核：保留保存、审核发布、启用地图三者的不同语义与条件。
- 巡检：地图点位、现场试拍和确认结果形成清晰主次，保留原有点位、任务、记录与舵机操作能力。
- 故障：按网页未提交、上位机处理、车端健康拒绝、导航执行失败区分；请求 ID 与真实日志关联继续保留。

预览新增的“地图与工程／任务记录／设备诊断”是导航组织提案，正式实现只能聚合已有能力。没有现成功能的入口不作为可点击的正式菜单上线。面积／时间等预览指标只有在现有状态提供可靠来源时采用，否则删除或明确显示不可用，不能保留示例数值。

## 阶段、风险与验收

### 第一阶段：两页 UI 实现与隔离回归（已确认并完成）

确认总体方案后，建立含当前未提交网页内容的专用检查点，核对冻结发布版中必须保留的恢复／返程／手机修复。先在独立候选目录实现，避免源码链接直接改变运行资源。

范围是两页布局、样式、必要的展示组件与呈现逻辑；保留框架、网关、ROS 控制和既有状态契约，不新增关键运行依赖。实现时保持现有选择器／事件接口，确需调整则同步对应浏览器回归。

验收：生产前端构建；已有相关 JS／Vitest／浏览器回归；待命、运行、暂停、恢复、返程、保存、审核、断线、超时等状态回放；桌面、平板、手机截图；长文本和滚动检查；停车、取消和恢复入口可访问；真实数据未到达时不能显示成功。保留原失败证据和未覆盖项。

回退：独立候选目录可弃用，按专用检查点逐文件还原本轮更改；不使用破坏性 Git 清理，不还原其他未提交工作。上线前当前发布保持原样。

### 第二阶段：验证后的页面上线（已批准并完成；下文保留原提案）

提供最终截图、回归结果、实际资源差异和明确发布／回退清单后，再确认上线。只发布经验证的 UI 资产；若实际需要改 systemd 或其他系统配置，按项目要求做同目录唯一备份、写维护记录并准备回滚。本阶段不自动包含实车运动测试。

主要风险是布局改变后遮挡停车／触控区域、前端状态分支误隐藏操作、源码和发布版本错配。以上隔离回归和版本核对针对这些风险；单纯 CSS 构建成功无法排除它们。

# 巡检行为树框架调研

调研日期：2026-10-10。本文是选型依据，不是当前启动入口、实机通过记录或完整业务设计。

当前设计入口为 [巡检应用包说明](../../src/carcar_inspection/README.md)；长期架构取舍见 [工业级优化建议与学习路线](../工业级优化建议与学习路线.md)。操作命令仅维护在 [操作手册](../操作手册.md)，当前实机结果以 [测试记录](../测试记录.md) 为准。

## 1. 范围与证据

本轮只进行设计与目录整理，不实现最小运行骨架，不引入以下候选项目的代码，也不启动底盘、串口、云台或导航节点。

本机只读查询确认 Nav2 为 `1.1.20`，`behaviortree_cpp_v3` 为 `3.8.7`，`nav2_route` 为 `1.1.20`。仓库 `carcar_navigation` 的 `package.xml` 与 `CMakeLists.txt` 已依赖 `rclcpp_action`、`nav2_behavior_tree` 和 `behaviortree_cpp_v3`；已有导航 BT 插件与恢复测试，不能把业务设计当作重写导航层的依据。

首版范围是单层室内、人工看护：固定巡检点 → 停稳 → 单轴俯仰 → RGB 拍照 → 车端本地保存并排队传给上位机。首版不在车端进行目标识别；上位机内部处理与传输协议后续决定。2026-10-11 的深度移动 Nav2 验证是计划，不是已通过结论。

## 2. 三个代表方案

| 方案与固定参考版本 | 官方能力与许可证 | 本项目取舍 |
|---|---|---|
| BehaviorTree.CPP `3.8.7` + Nav2 `1.1.20` Action | BT.CPP 提供可组合的执行树与异步节点；Nav2 暴露导航 Action。BT.CPP 为 MIT；此处涉及的 `nav2_behavior_tree` 为 Apache-2.0 | 推荐主线。应用树编排巡检步骤，现有导航树完成单次导航。沿用 v3，避免无需求升级现有插件 |
| Nav2 Waypoint Follower `1.1.20` | 顺序访问点位，反馈当前索引，返回未完成点；TaskExecutor 插件可执行到点等待、拍照等动作。包许可证 Apache-2.0 | 作为简单串行任务的学习与验收对照；可取消的云台采集、多步骤异常与持久化仍需应用层明确处理 |
| PlanSys2 `2.0.9` | PDDL 任务规划并通过行为树执行；此版本 executor 依赖 `behaviortree_cpp_v3`，包声明 Apache License, Version 2.0 | 暂缓。任务顺序需要根据资源、前置条件和优先级自动推导时再评估；当前固定点位拍照不足以抵消额外领域模型和规划器维护成本 |

上述能力分别来自 [BT.CPP 3.8 异步教程](https://www.behaviortree.dev/docs/3.8/tutorial-basics/tutorial_04_sequence/)、[BT.CPP 3.8.7 许可证](https://github.com/BehaviorTree/BehaviorTree.CPP/blob/3.8.7/LICENSE)、[Nav2 1.1.20 导航 Action 定义](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_msgs/action/NavigateToPose.action)、[Nav2 1.1.20 BT 依赖与许可证](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_behavior_tree/package.xml)、[Waypoint Follower 1.1.20 官方说明](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_waypoint_follower/README.md)、[Waypoint Follower 1.1.20 许可证](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_waypoint_follower/package.xml)、[PlanSys2 官方设计](https://plansys2.github.io/design/index.html)与 [PlanSys2 2.0.9 executor 依赖及许可证](https://github.com/PlanSys2/ros2_planning_system/blob/2.0.9/plansys2_executor/package.xml)。PlanSys2 在线设计页会随上游更新，具体接口须按固定版本复核。

## 3. 图中接口需要修正的地方

### 3.1 Simple Commander 与 C++ Action

Nav2 Simple Commander `1.1.20` 明确面向 Python3，封装导航 Action、反馈和取消。它适合作为接口学习来源，但项目后续可执行逻辑统一使用 C++，因此设计图中的该模块改为 C++ Nav2 Action 适配器，通过 `rclcpp_action` 调用同一导航服务端，不复制整套导航系统。[官方固定版本说明](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_simple_commander/README.md)

本版本 `NavigateToPose` 请求包含目标 `PoseStamped` 与导航树路径，反馈包含当前位姿、导航时长、剩余距离和恢复次数；其结果消息本体是空字段，不能照搬新发行版的错误码字段。业务层须结合 Action 终态与本项目诊断生成自己的错误分类。[1.1.20 Action 定义](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_msgs/action/NavigateToPose.action)

### 3.2 导航树与巡检树

Waypoint Follower 官方说明明确把简单多点任务与更复杂的机器人自主任务分开，并建议后者使用应用层行为树。本项目据此选择：导航树负责到一个位置的规划、跟随和有限恢复；巡检树负责点位顺序、停稳、俯仰、采集和记录；任务管理负责对外状态及持久化。[1.1.20 官方职责讨论](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_waypoint_follower/README.md)

这是职责划分建议，不要求首版拆成多个独立进程。异步叶节点应快速返回 `RUNNING`，取消需传播到在途操作；树被 halt、Action 接受取消、Action 返回终态与车辆物理停稳不能混作同一个事实。[BT.CPP 3.8 异步说明](https://www.behaviortree.dev/docs/3.8/tutorial-basics/tutorial_04_sequence/)

### 3.3 BehaviorTree.ROS2 的版本约束

BehaviorTree.ROS2 `0.3.0` 提供 ROS Action、Service、Topic 包装和树执行服务，但明确要求 BT.CPP `4.6` 或更新版本，以及 ROS 2 Humble 或更新版本。支持 Humble 不等于兼容现有 BT.CPP v3 插件；不能直接把它混入本车 Nav2 v3 插件进程。首版继续沿用现有 v3 接口，独立 v4 进程方案只有出现明确收益时再评估。[固定 tag 0.3.0 要求](https://github.com/BehaviorTree/BehaviorTree.ROS2/blob/0.3.0/README.md)

### 3.4 官方巡检示例的证据边界

Nav2 `1.1.20` 的 [demo_inspection.py](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_simple_commander/nav2_simple_commander/demo_inspection.py) 演示固定货架巡检点、`followWaypoints`、索引反馈与返回起点，许可证为 Apache-2.0。示例注释也提出真实应用可从文件或示教读取路线。

该示例没有提供本项目所需的单轴俯仰验收、照片持久化队列和异常业务闭环。公开演示是可参考的接口使用案例，不能作为工业可靠性、产品认证或本车实机通过证据；本轮仅借鉴职责和调用方式，不引入 Python 可执行文件。

## 4. 与当前实车约束有关的工程推断

以下属于本项目设计推断与约束，尚需离线及现场验收，不是上游保证：

- **点位配置化**：`map` 下的停车位 `(x, y, yaw)`、被检查目标、单轴观察角和采集规则分开描述。车体 yaw 决定底盘朝向；云台俯仰改变镜头相对车体方向。固定点位能提高可复现性，但位置标定误差、遮挡和光照变化仍会影响照片质量。首版不增加动态目标搜索或视觉闭环对准。
- **角度证据分级**：发送的舵机命令值、软件估计角与实物反馈分别记录。缺少独立位置反馈时，`JointState` 与 TF 只能表达命令或估计姿态，不能单凭其证明舵机已到位。
- **相机视野互斥**：同一 D435 抬头拍摄会改变导航深度观测范围。首版先停车再改变观察姿态；行驶前恢复并验证导航姿态及深度健康。具体姿态、等待时间与恢复条件必须由实机结果确定，不能把“命令已发”当作可继续行驶依据。
- **深度层保留现有基线**：原图中的 VoxelLayer 不能覆盖当前已有 STVL 工作。保持现有 STVL 实验与历史 VoxelLayer 对照资产，深度移动导航仍按待验收计划推进，不提升为已通过默认能力。
- **单串口所有者**：巡检应用通过既有 ROS 接口调用底层能力，不另开控制板串口。正式驱动与底层测试不能同时占用串口；业务应用也不直接发布电机输出绕过现有保护。
- **异常有界**：故障反馈有等待预算，上报超时仍可结束，不能让网络阻塞无限拖住任务；用户已确认导航与采集故障采用不同灯色并结束整轮。详细配色、时序、存储失败边界及任务终态只维护在应用设计，不在研究记录重复。停车确认应先于网络等待，不能因云端确认迟到继续运动。

完整任务模型与异常表只维护在 [巡检应用包说明](../../src/carcar_inspection/README.md)，本文不重复维护操作命令和详细设计。硬件与当前实机证据分别见 [硬件台账](../硬件台账.md)和 [测试记录](../测试记录.md)。

## 5. 暂不引入的能力

`nav2_route` 在本机及上游 `1.1.20` 中确实存在，不能笼统说 Humble 没有 Route Server；但已安装不等于已接入或验收。需要单向通道、明确边约束或拓扑路线时再评估，首版先使用已部署地图上的目标位姿导航。[Nav2 1.1.20 Route 包定义](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_route/package.xml)

首版也暂不增加车端视觉识别、PDDL 自动任务规划、多机调度或以新框架替换现有导航恢复。后续是否加入这些能力，由具体业务缺口与可观测验收指标决定。

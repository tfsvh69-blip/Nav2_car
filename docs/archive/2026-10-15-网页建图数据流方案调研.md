# 网页建图数据流方案调研

归档日期：2026-10-15。资料核对时间：2026-10-14～15。本文保存官方资料、版本和本项目取舍依据；当前实现与进度见[项目现状与路线](../项目现状与路线.md)，验证结论见[测试记录](../测试记录.md)，完整有效命令统一见[操作手册](../操作手册.md)。本文不提供另一套启动入口。

## 1. 本轮采用的方向与证据边界

保留现有 C++ 网关、独立运动门控、WebSocket 控制以及 HTTP 地图/视频入口，按数据用途重新组织传输。借鉴成熟方案的按需订阅、限频、有界队列和明确的运动新鲜度，不在本轮引入 rosbridge、Foxglove、Transitive 或 WebRTC 依赖。

- **控制和安全状态优先保持轻量**：只携带操纵、挑战回应、使能/撤销及必要健康信息；地图、激光预览和视频独立更新。
- **状态按变化和用途发送**：激光预览使用自己的序号与更新频率，避免在相同数据未变化时随完整状态反复发送；没有使用的预览不持续请求。
- **缓冲有界且策略明确**：可替换的预览保留新值；正在异步写入的数据保持生命周期稳定；停车、撤销和会话变化不与普通预览使用模糊的统一丢弃规则。
- **运动许可由车端独立判断**：保留车端签发后的 300 毫秒截止、超时停车和重新使能要求，重连后不恢复历史运动请求。传输优化与运动门控分别验收。

本轮只读静止快照中，`/api/state` 约 20,270 字节，包含 439 个激光预览点；控制状态约 1,216 字节；地图 PNG 约 864 字节，`video_requested=false`。前端约 100 毫秒请求一次状态，后端扫描预览约 200 毫秒更新一次。这支持检查重复传输和前端处理负担，但不是所有场景的吞吐统计，不能由此认定视频、地图或某一协议就是超时的唯一根因。

下文的“官方支持”指对应版本的文档或实现存在该能力；“本项目采用”指设计取舍；性能收益、停车时间和无线稳定性仍需本项目实测。公开演示、源码可用和离线通过均不等同工业认证或本车实机验收。

## 3. 三类官方方案如何处理数据

### 3.1 rosbridge_suite：按话题订阅、限频，区分不同层的队列

rosbridge 把浏览器请求转换成 ROS 话题、服务和动作操作；roslibjs 提供对应 JavaScript 客户端。订阅可设置 `throttle_rate` 和 `queue_length`。`queue_length=1` 使 **ROS 话题到浏览器的订阅节流队列**在满时替换最旧消息，适合只关心最新状态的预览；它不自动给浏览器发往小车的运动请求添加过期时间。[固定版协议](https://github.com/RobotWebTools/rosbridge_suite/blob/2.0.8/ROSBRIDGE_PROTOCOL.md)、[订阅节流队列实现](https://github.com/RobotWebTools/rosbridge_suite/blob/54868a228d8c05cc60cb85d6e4813a3271283e31/rosbridge_library/src/rosbridge_library/internal/subscription_modifiers.py#L122)。

固定版 WebSocket 实现每连接默认收/发队列均为 1000 条。输入满时丢最旧，输出满时丢当前新消息；单个协程串行等待写入完成，连接建立后调用 `set_nodelay(True)`。这支持本项目借鉴 TCP_NODELAY、串行异步写和显式缓冲上限，不能概括成“所有队列都丢旧保新”。[固定源码：输入队列、连接设置、输出队列和写循环](https://github.com/RobotWebTools/rosbridge_suite/blob/54868a228d8c05cc60cb85d6e4813a3271283e31/rosbridge_server/src/rosbridge_server/websocket_handler.py)。

roslibjs 的 `Topic.publish()` 经过 `Ros.callOnConnection()`：断线期间调用会挂到下次连接时发送。因此通用客户端的自动恢复行为不能直接用于运动控制；`reconnect_on_close=false` 管理重新订阅/注册，也不能替代运动新鲜度检查。[Topic.publish](https://github.com/RobotWebTools/roslibjs/blob/5b60f744e45dc2e7ca9dace74727c27eddb93603/packages/roslib/src/core/Topic.ts#L246)、[断线发送行为](https://github.com/RobotWebTools/roslibjs/blob/5b60f744e45dc2e7ca9dace74727c27eddb93603/packages/roslib/src/core/Ros.ts#L177)。

本项目取舍：参考按话题分频和最新值语义，保持现有 C++ 控制入口，不用通用话题桥接代替独立门控。

### 3.2 Foxglove Bridge：原始序列化数据、按需订阅、有界积压

Foxglove Bridge 的 ROS 2 部分使用通用序列化订阅，把原始消息交给 SDK 发送；可按白名单开放话题并限制 ROS QoS 深度。连接声明某话题可用，与客户端实际订阅该话题是两个步骤，不应理解成“连接后自动把所有大话题都发给浏览器”。[ROS 2 订阅和消息转发实现](https://github.com/foxglove/foxglove-sdk/blob/115b582496834d07e6ac6e8acf5676a883c6aec6/ros/src/foxglove_bridge/src/ros2_foxglove_bridge.cpp)、[固定版配置说明](https://github.com/foxglove/foxglove-sdk/blob/ros-v3.6.0/ros/src/foxglove_bridge/README.md#configuration)。

SDK 每客户端分别设置数据面与协议控制面有界队列，`message_backlog_size` 默认 1024。数据面溢出时尝试丢最旧消息；协议控制面满时断开客户端。这里的“控制面”指声明、参数、服务等桥接协议消息，不代表小车速度命令自动获得优先权；数据面也不是每话题各有一套最新值缓冲。[队列结构和处理](https://github.com/foxglove/foxglove-sdk/blob/115b582496834d07e6ac6e8acf5676a883c6aec6/rust/foxglove/src/websocket/connected_client.rs)、[丢最旧实现](https://github.com/foxglove/foxglove-sdk/blob/115b582496834d07e6ac6e8acf5676a883c6aec6/rust/foxglove/src/websocket/connected_client/send_lossy.rs)。

收、发循环并发执行，但两类输出最终仍串行写入同一个 WebSocket。应用队列丢弃旧消息不能移除已经写入 TCP 的数据，也不能保证无线中断期间继续满足控制截止。[收发循环](https://github.com/foxglove/foxglove-sdk/blob/115b582496834d07e6ac6e8acf5676a883c6aec6/rust/foxglove/src/websocket/connected_client/poller.rs)。

SDK 客户端消息封装只有通道和载荷，服务器输出另有 `log_time`；服务器 `session_id` 用于数据会话重置。这些字段本身不是操纵权租约、运动期限或停车规则。[客户端消息结构](https://github.com/foxglove/foxglove-sdk/blob/ros-v3.6.0/rust/foxglove/src/protocol/common/client/message_data.rs)、[服务器时间字段](https://github.com/foxglove/foxglove-sdk/blob/ros-v3.6.0/rust/foxglove/src/protocol/v1/server/message_data.rs)、[会话重置](https://github.com/foxglove/foxglove-sdk/blob/ros-v3.6.0/rust/foxglove/src/websocket/server.rs#L607)。

旧 `ws-protocol` 文档已经注明过时、库停止维护并建议迁移 SDK；本轮不照旧文档自写 Foxglove 兼容服务器。[官方弃用说明](https://github.com/foxglove/ws-protocol/blob/main/docs/spec.md)。如以后需要通用三维诊断，可单独评估 C++ Bridge、只开放观察话题并关闭 `clientPublish`；本轮不增加该入口。

### 3.3 Transitive：将操作者实际看到的数据与运动新鲜度关联

官方 Remote Teleop 使用 WebRTC 传输视频和控制；公开行为包括主动拖动才发送运动、显式使能，以及延迟超过 500 毫秒停止发送。其 `Joy`、`PointStamped` 使用浏览器最近接收视频帧对应的机器人时间，判断这条请求所依据的观察是否仍新鲜；v0.16 变更说明的控制默认频率为 20 Hz。这是公开产品行为，不是本项目实测。[官方安全功能与版本记录](https://www.transitiverobotics.com/caps/transitive-robotics/remote-teleop/)。

可借鉴的是“运动请求应关联可验证的新鲜观察”，而不是只检查连接还在或消息刚到达。本项目已有车端挑战回应，视频关闭时仍须独立保持运动新鲜度；不为照搬视频关联而强制打开相机，也不把该产品的 500 毫秒替换成本车门限。Transitive 的本地模式仍有周期联网取得计费令牌的条件，不能作为完全离线的开源替换方案。

## 4. 后续 WebRTC 候选与本轮不引入的原因

`libdatachannel v0.24.6` 于 2026-09-26 发布；固定提交 `6b1e2e620f1e37f0eafeee702eaea0043cb305fd`，MPL-2.0。它提供 C/C++ WebRTC 数据通道、媒体和 WebSocket 能力，可作为未来 C++ 传输实验候选；本轮只登记来源，不新增依赖、构建选项或运行服务。[发布记录](https://github.com/paullouisageneau/libdatachannel/releases/tag/v0.24.6)、[固定版 README](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/README.md)、[LICENSE](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/LICENSE)。

WebRTC 数据通道默认有序，未设置重传次数/时间限制时仍使用可靠传输。`ordered`、`maxRetransmits`、`maxPacketLifeTime` 需要明确选择；仅把 WebSocket 换成 WebRTC，并不自动获得“旧指令立即丢弃”或运动停车保证。[W3C 2025-03-13 固定推荐标准：RTCDataChannelInit](https://www.w3.org/TR/2025/REC-webrtc-20250313/#dom-rtcdatachannelinit)。

本轮优先修复已存在的数据重复、调度与缓冲可观测性。未来若实验 WebRTC，还需单独处理会话协商、连接恢复、媒体编码与车端期限；保持独立门控，并与现有入口在同一网络、相同预览负载和速度条件下比较。

## 5. 采用后的验收原则

- **预览与控制分别计量**：统计各通道字节量、更新次数、重复跳过次数及队列覆盖次数；画面刷新频率不代表运动请求的新鲜度。
- **定位等待发生在哪一段**：关联车端签发、网关等待/写入完成、浏览器处理和回应到达；跨设备时间不直接相减，车端截止使用车端自己的时间依据。
- **正常与故障场景并测**：覆盖静止、持续推杆、松手、前后台切换、突发积压、断连与重连。有效请求应连续控制；过期请求、旧会话和断流必须停车，恢复通信不得自动恢复运动。
- **保持证据层级**：源码阅读证明设计存在，替身/隔离域测试证明离线行为，真实浏览器与现场停车结果才证明本车本轮表现。即使应用排队消除，真实无线中断仍可能触发保护，不能以扩大缓冲或延长旧指令许可宣布问题解决。

当前方案保留，具体接口、离线结果与实机反馈随本轮实现分别更新到对应当前文档；本文作为固定调研依据归档，不持续复制现场测试日志。

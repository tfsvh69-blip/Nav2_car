# 动态调参与连续探索讨论（2026-11-03）

状态：**调研与方案讨论，尚未实施。** 本文不表示参数面板、连续探索、玻璃识别或任何新配置已部署。本轮不修改正式参数、不启动硬件、不发送运动请求；先保留当前改善后的正式 r2 基线。当前发布事实以[项目现状与路线](../项目现状与路线.md)为准。

## 1. 本轮问题与证据边界

用户现场反馈：当前前进与转弯明显改善，未再看到车头左右摆动；探索到较极端的目标附近仍花较长时间调整方向，下一点有时在身后；临时放入小障碍后，目测约三倍车宽的通道仍会停止自动前进；固定大玻璃墙未被雷达正确观测。希望网页可在线调节全局／局部代价参数及接近目标后的续接距离。

以上属于本轮**现场定性反馈**。三倍车宽不是已量测通道几何，目标切换、停止层级、自动负速度和玻璃表面距离还需本轮日志或独立静止观测确认。不能据反馈直接认定全局膨胀是停车主因，也不能把软件速度命令或轮式位置当作实物运动测量。

## 2. 网页动态调节代价地图

### 来源事实：现有版本支持在线修改

本机使用 ROS 2 Humble／Nav2 1.1.20。该固定版本的 `InflationLayer` 为 `inflation_radius` 和 `cost_scaling_factor` 注册动态参数回调；值变化后重算缓存，并在后续地图更新中重新膨胀。因此可以由现有 C++ 网关调用 ROS 2 参数服务，无需为了这两项参数重启导航或手动编辑 YAML。[Nav2 1.1.20 动态回调源码](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_costmap_2d/plugins/inflation_layer.cpp#L403)

| 参数 | 对实际行为的含义 | 当前 r2 基线 |
|---|---|---:|
| 全局 `inflation_layer.inflation_radius` | 规划使用的障碍周围代价覆盖范围 | 0.50 m |
| 全局 `inflation_layer.cost_scaling_factor` | 该范围内代价的指数衰减系数 | 3.0 |
| 局部 `inflation_layer.inflation_radius` | 局部控制使用的代价覆盖范围 | 0.30 m |
| 局部 `inflation_layer.cost_scaling_factor` | 局部代价的指数衰减系数 | 5.0 |

当前值来自[正式参数与发布记录](2026-11-02-自动建图稳定性优化与参数部署/README.md)，是配置基线，不是本轮新做的运行参数读回。

`cost_scaling_factor` **越大，代价随距离下降越快**；越小则衰减更缓。`inflation_radius` 是覆盖范围，不能简单理解成车身外侧必须额外留出的距离。[固定版本代价公式](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_costmap_2d/include/nav2_costmap_2d/inflation_layer.hpp#L140)

### 来源事实：软代价与硬拒绝不同

膨胀区域包含接近障碍的高代价及更远处的软代价。软代价会影响路径选择和控制减速，整个彩色膨胀区域并不都是禁行区。本项目还保留原图未知区拒绝、0.22 m 硬净空、规划掩膜、原始激光及执行扫掠检查；这些不是一个膨胀半径滑块的不同名字。[Nav2 代价公式](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_costmap_2d/include/nav2_costmap_2d/inflation_layer.hpp#L140)、[本项目软硬分层证据](2026-11-02-自动建图稳定性优化/README.md)

**本项目判断：** 仅凭网页颜色或目测通道宽度不能判定停车来自哪层。下一轮应把同一请求／目标 UUID 对应的规划结果、当前车位净空、原始回波、执行扫掠及数据年龄放在一起看，再决定调全局偏好、局部减速或其他环节；不通过缩小硬净空绕过原因。

### 来源事实：局部代价与 RPP 有参数耦合

Humble 1.1.20 RPP 使用 `inflation_cost_scaling_factor` 把局部栅格代价反算为障碍距离，再按 `cost_scaling_dist` 减速。局部膨胀的衰减系数改变时，应同步保持 `FollowPath.inflation_cost_scaling_factor` 一致，避免控制器解释错误；减速距离还需与膨胀覆盖范围协调。这两项 RPP 参数均有动态回调。[距离反算及减速实现](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_regulated_pure_pursuit_controller/src/regulated_pure_pursuit_controller.cpp#L589)、[动态回调](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_regulated_pure_pursuit_controller/src/regulated_pure_pursuit_controller.cpp#L759)

### 来源事实与设计建议：生效确认和恢复

ROS 2 `SetParametersAtomically` 是**单节点**服务。一次调用不能同时原子修改全局代价图、局部代价图和控制器三个节点；普通 `SetParameters` 还允许参数逐项成功或失败。[ROS 2 Humble 参数服务实现](https://github.com/ros2/rclcpp/blob/humble/rclcpp/src/rclcpp/parameter_service.cpp#L70)

建议网页复用现有 C++ 网关，采用以下闭环：

1. 读取真实参数和当前任务身份，显示节点离线、初始化或可调状态。
2. 校验类型、范围和局部膨胀／RPP联动条件，保存本次旧值与 `request_id`。
3. 同节点参数使用原子请求，跨节点由网关顺序编排；失败时尝试恢复旧值并明确报告恢复结果。
4. 读回各节点确认，再等待相应代价图更新。区分“请求已受理”“参数读回一致”和“新代价图已生成”。
5. 页面显示请求值、读回值、当前应用状态及失败原因；刷新或重连后重新读取。滑块防抖或松手提交，避免连续整图重算。
6. “仅本轮在线生效”与“保存为下次配置”分开，提供恢复本轮基线及变更记录。保存成功不改变当前 r2 的历史发布指纹与验收声明。

这是建议的实现范围，尚未确定可调数值上下限和默认交互，也没有实现、测试或发布。足迹、硬净空、未知区拒绝、命令超时和自动短退不纳入普通代价调节面板。

## 3. 接近目标后的连续衔接

### 来源事实：官方已有多点连续导航机制

Nav2 1.1.20 的 `NavigateThroughPoses` 示例使用 `RemovePassedGoals → ComputePathThroughPoses → FollowPath`：中间点进入通过半径后从待规划列表删除，再规划剩余点；沿同一多点路线继续跟踪，最终点才结束整段任务。该固定版本示例半径为 0.7 m，类默认值为 0.5 m；都不是本车已经标定的参数。[固定版本行为树](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_bt_navigator/behavior_trees/navigate_through_poses_w_replanning_and_recovery.xml)、[中间点移除实现](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_behavior_tree/plugins/action/remove_passed_goals_action.cpp#L38)

本项目已保留默认关闭的连续探索候选，使用 `RemovePassedGoals`、实际规划路径检查及探索专用 GoalChecker。当前正式 `continuous_exploration=false`；历史完整效率门槛未通过，不能仅打开开关就称为优化完成。[连续探索归档](2026-10-30-行进中一致快照集成验证.md)、[项目行为树](../../src/carcar_mapping_autonomy/behavior_trees/navigate_through_poses_exploration.xml)

官方示例中的清图、`Spin` 和 `BackUp` 不作为本项目自动采用项。可以复用其中的中间点和路线续接机制，保留本项目原有取消、停稳、净空及恢复边界。

### 设计建议：先做稳定两点前瞻

建议先比较“当前单目标”和“稳定的当前点＋下一点”两种方式：在到当前点之前计算并验证下一观测点，有有效续接路线时继续通过；下一点无效或任务需要暂停时仍执行原停车流程。网页可开放**提前准备距离**与**中间点通过距离**，两者分别负责提前计算和真正切换，不与返程最终到点容差混用。

提前准备／切换距离应以**沿当前有效路径的剩余距离**为主要依据，并结合地图连通、方向和观察收益；仅用车位到目标的欧氏直线距离，可能隔墙误判“已经接近”。下一点还应考虑实际路程、转向代价、可见未知区域及重复访问，减少先去极端点、再大幅掉头。

这是适配本项目的建议，不是对所有机器人系统的统一结论。还需处理地图增长、目标失效、回环／重定位后的坐标代次、取消与迟到反馈、路线折返及末端停车；避免每次地图更新都取消重发，也不能用过大的通过距离跳过尚未充分观测的区域。

软件验收应同时记录完整任务完成、地图覆盖、总路程、转向耗时、启停次数和失败恢复；不能只用路程缩短或单个点更快作为连续探索通过依据。现场还需分别验证实物平顺、障碍避让和停车。

## 4. 本轮转向与“倒车”尚需核对

**已确认配置事实：** 正式 r2 的探索行为树绑定 `PositionGoalChecker`，XY 容差 0.15 m，不要求终点 yaw 成功；返程仍保留起点朝向验收。Shim 的 `rotate_to_goal_heading=true` 仍保留。[探索行为树](../../src/carcar_mapping_autonomy/behavior_trees/navigate_to_pose_exploration.xml)、[正式控制配置](../../src/carcar_mapping_autonomy/config/controller_shim_rpp.yaml)、[Nav2 PositionGoalChecker](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_controller/plugins/position_goal_checker.cpp#L60)

**实现边界与推断：** Shim 在进入位置容差时可能计算末端旋转；Nav2 1.1.20 ControllerServer 每周期先计算／发送速度，再检查目标到达，因此存在末端单周期旋转的可能。它不足以解释用户观察的持续调头。本轮必须按动作 UUID、目标位置、路径方向、最终速度和到达终态，区分旧目标末端、下一目标起步或重规划转向，不能仅凭“到点附近转头”直接修改返程朝向。[本项目 Shim](../../src/carcar_mapping_autonomy/include/carcar_mapping_autonomy/mapping_rotation_shim.hpp)、[官方控制循环](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_controller/src/controller_server.cpp#L374)

此前对称探索 v6 审计确实把额外长转向定位为新目标起步，但那是历史软件场景，不能直接套用到本次现场。[历史 yaw 审计入口](2026-11-02-自动建图稳定性优化与参数部署/README.md)

**自动倒车未确认：** 当前 RPP `allow_reversing=false`，速度平滑器前进下限为 0，自动短退关闭。用户所说“需要倒车”可能指下一目标在身后而需要掉头，或需要人工倒退解困；本轮尚未证实自动导航输出了负向速度。[RPP 配置](../../src/carcar_mapping_autonomy/config/controller_rpp.yaml)、[建图平滑器配置](../../src/carcar_mapping_autonomy/config/nav2_mapping.yaml)

## 5. 玻璃墙与反射率

### 来源事实：现有雷达与历史结果

硬件台账登记为 **RPLIDAR A1**；URDF 名义扫描中心相对 `base_footprint` 高度为 **0.217 m**。这是安装配置值，不是本轮新增独立测量。[硬件台账](../硬件台账.md)

2026-10-28 `LIDAR-GLASS-001` 已对当时左侧固定玻璃进行静止对照。用户当时粗估玻璃距车身中心约 0.40 m；Standard、Express 各完整采样 103 帧，左侧 80°～100°扇区在 0.30～0.50 m 诊断距离带中均为 **0 点**。数据按既有 URDF 转到 `base_footprint`，X前、Y左；该距离带只是围绕粗估位置的诊断分箱，不代表已量得玻璃平面，也不适用于移动车辆后的当前距离。[历史原始结论与边界](2026-10-28-自动建图切点诊断/README.md)

本机 ROS 驱动发布的 `intensities` 来自 `quality >> 2`；Express SDK 对有效点填入固定质量码，ROS 中表现为 **47**。它不是经过标定的玻璃材料反射率。Standard 质量码存在变化，但历史对照也未找到玻璃表面距离，因此筛选质量上下限无法生成原始数据里没有的墙面回波。[驱动发布代码](../../src/sllidar_ros2/src/sllidar_node.cpp)、[Express SDK 质量赋值](../../src/sllidar_ros2/sdk/src/dataunpacker/unpacker/handler_capsules.cpp)、[历史对照](2026-10-28-自动建图切点诊断/README.md)

### 结论边界与建议

在本机现用驱动和已核查公开接口范围内，**没有找到可供网页调节的“材料反射率／玻璃灵敏度”接口**。`scan_mode`、质量筛选和扫描频率不等同于改变玻璃本身的反射率，也不能承诺把玻璃调成可见。历史结论仅适用于当时角度和玻璃，没有证明所有角度、所有玻璃永远无回波。[现用驱动参数](../../src/sllidar_ros2/src/sllidar_node.cpp)、[历史对照](2026-10-28-自动建图切点诊断/README.md)

SLAMTEC 官方对透明、镜面或吸光物体的建图建议，是在雷达扫描平面覆盖适合扫描的其他材料。[官方建图说明](https://www.slamtec.com/en/news/detail/813)

因此优先讨论两种清楚区分的方案：

- **真实入图方案：** 在玻璃扫描高度附近连续覆盖足够宽的哑光、不透明、可产生漫反射的材料。名义参考高度约 217 mm，实际需覆盖当前扫描平面而非只贴一条可能扫不到的细线；先静止观察原始激光是否形成真实连续表面，再判断 SLAM 是否正确入图。这是建议，尚未获得本轮贴好及复测成功证据，不把“贴条”直接记作玻璃识别已完成。
- **规划约束方案：** 在测量或可靠配准的位置建立虚拟墙／禁行区，约束规划避开玻璃。它是人工已知边界，**不是雷达识别成功**，也不能伪装成原始扫描或 SLAM 自主测得的玻璃墙。当前未实施。

若环境不允许覆盖材料，需另行评估不同传感器对透明物体的可观测性；不能默认已有 D435 深度即可可靠识别玻璃，也不在本轮讨论中直接扩展到新硬件采购。

## 6. 后续讨论的推荐顺序

1. 保留用户已确认明显改善的正式 r2，完整保存源码、配置和未解决问题，当前不启用历史连续、排序或自动短退候选。
2. 优先做可读回、可恢复的全局／局部参数面板，把当前参数与停车拒绝层级显示清楚；同场景每次改变一组相关参数，保留对照证据。
3. 根据本轮 UUID／速度／路径确认转向与所谓倒车发生在哪一阶段，再做稳定两点前瞻和路径剩余距离可调的独立候选，分别验收效率与停车。
4. 玻璃优先通过扫描平面漫反射覆盖＋静止原始回波确认；需要虚拟墙时明确其人工约束性质。

本轮只形成以上事实核对和建议，没有执行这些后续实现或实车验证。

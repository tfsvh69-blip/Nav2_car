# NAV-018-R21 建图网页操作流程与UI验收

日期：2026-10-29。范围为建图网页及巡检入口衔接，实车基线仍是R20；本轮不启动底盘／雷达，不发布、启用真实地图，不修改系统配置。

## 问题与选定方案

网页基础功能已具备，但操作层级混杂：自动运行仍突出遥控与不可用的开始按钮，启动区会在启动中消失；重复点击能在轮询前再次提交；操作反馈会被通用状态覆盖；候选已保存仍可能显示等待保存，审核与启用条件不够直观。实际巡检入口还因仅网页服务未运行返回502。

沿用已有HTML／JavaScript／CSS及视觉风格，增加紧凑的阶段引导和适用控件，修正请求与事实反馈，不引入新前端框架、通信协议或依赖。相比重做整页，局部调整保留成熟控制通道、地图绘制和底层安全链路；相比仅改文案，本轮同时修正重复提交、迟到反馈和完成态语义。

参考成熟实现，按本项目约束适配，没有复制第三方代码：

| 来源 | 适配要点与边界 |
|---|---|
| [Foxglove Teleop官方说明](https://docs.foxglove.dev/docs/visualization/panels/teleop) | 遥控面板依赖实时控制连接，并明确松手停止。借鉴模式与控件边界，保留本项目既有门控、期限和停车规则，不套用其默认发布频率 |
| [Nav2 Humble Commander官方实现](https://api.nav2.org/nav2-humble/html/robot__navigator_8py_source.html) | 请求、任务完成与取消结果分开。网页等待既有车端终态／停稳，不把HTTP成功当物理动作完成；不新增Python车端节点或切换ROS发行版 |
| [W3C状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | 使用可被辅助技术识别、无需抢焦点的状态区域。保留明确文字反馈，减少提示闪烁；没有据此宣称完整无障碍认证 |

## 最终交互

- 准备：新建／续建与手动／自动分开；自动需本轮场地确认，启动即时锁定，启动中保留进度和控制方式。
- 建图：自动时收起遥控与不适用按钮，暂停、接管和返程按阶段出现；手机任务操作置于地图前。手动接管后显示原摇杆，停车入口始终保留。
- 请求：同一次request_id贯通反馈。受理、取消中、轮式停稳、保存分别说明，已确认结果优先于迟到HTTP超时；离线不重发，不声称自动任务已经停车。
- 结束：候选保存后只突出结束并查看候选；明确返程结果与待审核，故障停稳后可正常结束，不自动恢复或返程。
- 审核：有效非诊断候选与现场结论齐全才可审核，已发布版本才提供启用；刷新保留选择，结束后优先选本轮候选。实际地图加载与重新定位仍须纯激光定位入口，配置页不替代它。

实际8080建图／巡检页面已通过只读浏览器检查。巡检仅网页服务通过既有XML入口启动，hardware_enabled、navigation_enabled、goal_navigation_enabled均false；不会因此启用执行器或实车导航。该运行入口没有安装为新的systemd服务。

## 验证与证据边界

1. 重复启动反例先失败后通过，原始红色日志保留；原任务状态、手动控制及RTC回归通过。
2. 选定CTest四组通过（49个C++内部用例及任务状态脚本），无C++生产修改。
3. 真实Chromium的12类交互夹具通过，覆盖桌面1366×900、平板1024×768、手机390×844、迟到应答、断线恢复、保存与故障结束；夹具HTTP／控制消息为测试数据。
4. 两轮真实HTTP／WebSocket、prepare、SLAM／Nav2软件生命周期通过，无HTTP替身；每轮有独立模拟轮式位移≥0.15米，最终完整保存并回待命。传感器为软件数据，不能算实车或完整覆盖。
5. 实际8080建图→巡检→建图、手机布局通过；pageerror=0、POST请求0，未访问执行器。新版触屏现场操作、真实无线故障与长时稳定性未验收。

# 网页建图 WebRTC 控制通道调研

日期：2026-10-15，范围：R9 的 LAN 数据控制通道。R8 后用户仍反馈浏览器心跳超时；本轮改为评估并新增可对照的传输路径，不能由此宣称 Wi-Fi 或超时根因已经修复。前一轮通用桥接比较见[数据流方案调研](2026-10-15-网页建图数据流方案调研.md)；当前实现、验收及完整有效命令分别见[项目现状与路线](../项目现状与路线.md)、[测试记录](../测试记录.md)、[操作手册](../操作手册.md)。

## 1. 采用的范围与工作原理

保留 C++ Safety 的车端签发后 300 毫秒截止和旧 WebSocket 入口；新增 `libdatachannel v0.24.6` 的 LAN `RTCDataChannel` 控制路径。最终实现复用原 `/ws/control` WebSocket 交换会话和 RTC 信令，不新增 HTTP 信令端点；HTTP 负责页面、地图和状态预览。本轮不调用 `getUserMedia`、不加入音视频轨道，也不依赖外部 STUN/TURN 服务。

WebSocket 经 TCP 可靠有序传输，丢失的旧数据可能阻挡后续数据；RTCDataChannel 使用 SCTP/DTLS/ICE，允许显式选择乱序、有限重传。R9 选择 `ordered=false, maxRetransmits=0`，目标是减少等待旧控制消息重传的机会；仍可能丢包、积压或受无线中断影响，运动有效期由 Safety 单独执行。[RFC 8831：协议与部分可靠性](https://www.rfc-editor.org/rfc/rfc8831.html)、[固定版可靠性定义](https://github.com/paullouisageneau/libdatachannel/blob/6b1e2e620f1e37f0eafeee702eaea0043cb305fd/include/rtc/reliability.hpp)。

“无外部 STUN 服务器”不等于完全没有 STUN 报文：局域网的 ICE 连通性检查仍使用该协议。信令负责交换 SDP、候选地址和会话标识，控制建立后通过 DataChannel 双向发送；不把信令往返用于每个运动周期。[RFC 8445：候选与检查](https://www.rfc-editor.org/rfc/rfc8445.html#section-2)、[固定版信令回调接口](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/README.md#signal-a-peerconnection)。本项目把会话、SDP、candidate、`rtc_status` 放入 `/ws/control` 的有界可靠信令队列，最多等待 16 条；满时关闭连接并按门控规则锁停，避免无限积压。它与乱序、零重传的控制 DataChannel 分别承担连接建立和运动更新。

## 2. 浏览器 HTTP、可靠性参数与消息大小

### 普通 HTTP LAN 页是否能用

W3C 2025-03-13 固定推荐标准中，`RTCPeerConnection`、`RTCDataChannel` 未加 `[SecureContext]` 限制；Chromium 官方接口定义也未标该限制。因此，只建立数据通道不能直接套用“必须 HTTPS 才能使用摄像头”的结论。`MediaDevices/getUserMedia` 才有明确的安全上下文要求。[W3C PeerConnection 接口](https://www.w3.org/TR/2025/REC-webrtc-20250313/#interface-definition)、[W3C DataChannel 接口](https://www.w3.org/TR/2025/REC-webrtc-20250313/#rtcdatachannel)、[Chromium 接口定义](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/peerconnection/rtc_peer_connection.idl)、[Media Capture 规范](https://www.w3.org/TR/mediacapture-streams/#navigator-interface)。

本项目应检测 `RTCPeerConnection` 是否存在，并以实际浏览器的建连结果为准；不因 `window.isSecureContext=false` 就预先禁用纯 DataChannel。浏览器版本、设备或管理策略仍可能限制连接，须记录实际版本与错误。这里的普通 HTTP 指页面来源，RTC 信令实际复用该页面对应的 `/ws/control` WebSocket；普通 HTTP 页面使用的 `ws://` 信令仍是明文，DTLS 加密不等于该明文信令来源已获认证，本轮适用边界为现有受控 LAN。

### 参数如何对应

| 浏览器参数 | C++ `rtc::Reliability` | 含义与约束 |
|---|---|---|
| `ordered=false` | `unordered=true` | 允许消息乱序到达；应用必须依靠会话与递增序号拒绝倒退消息 |
| `maxRetransmits=0` | `maxRetransmits=0`，该 optional 必须处于已设置状态 | 允许初次发送，不做该数据消息的 SCTP 重传；不是“禁止发送” |
| 不设置 `maxPacketLifeTime` | 保持该 optional 未设置 | 不能与 `maxRetransmits` 同时设置；浏览器规范要求同时设置时抛错 |

默认参数仍是有序可靠；仅设置乱序不会自动关闭重传。C++ 的 `maxRetransmits` 是 optional，值为零与“未设置”不同。服务端收到通道后可通过 `reliability()` 检查实际设置，不应只相信前端声明。[W3C 参数](https://www.w3.org/TR/2025/REC-webrtc-20250313/#dom-rtcdatachannelinit)、[固定版可靠性头文件](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/include/rtc/reliability.hpp)、[固定版 DataChannel 接口](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/include/rtc/datachannel.hpp)。

消息大小由双方 SDP 协商及本地限制共同决定，不能把浏览器某次默认值当通用上限。固定版主库的本地默认上限为 256 KiB，远端未声明时按 65,536 字节处理，最终取较小限制；可查询 `maxMessageSize()`。控制保持小消息，并额外使用应用自己的严格长度上限，地图、激光数组与诊断长文本不进入此通道。[固定版常量](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/src/impl/internals.hpp)、[协商限制计算](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/src/impl/peerconnection.cpp#L118)。

`maxRetransmits=0` 不能替代缓冲管理：该固定版 `SctpTransport` 仍有发送队列，立即发送失败后会入队。前后端必须观察 `bufferedAmount`，限制排入的控制消息并记录跳过/积压；已经排入库的旧运动消息即使后来到达，也须被 Safety 的期限和序号拒绝。[固定版发送队列](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/src/impl/sctptransport.cpp#L159)、[发送行为](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/src/impl/sctptransport.cpp#L374)。

## 3. LAN ICE 与 mDNS 的边界

`iceServers=[]` 仍可收集本地 host 候选；双方地址可达、UDP 允许且无线接入点没有客户端隔离时，可以直接建立 LAN 连接。没有外部 STUN/TURN 时，不提供跨 NAT、公网中继或被隔离子网的连通保证；HTTP 网页能打开，只能说明网页的 TCP 路径可达。[RFC 8445 host 候选](https://www.rfc-editor.org/rfc/rfc8445.html#section-5.1.1.1)、[固定版 ICE 配置](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/include/rtc/configuration.hpp)。

浏览器可能用随机 `.local` 名称隐藏 host IP。固定版主库将无法按数字地址解析的候选交给异步 `Candidate::resolve(Lookup)`，最终依赖系统 `getaddrinfo`；README 声明支持 mDNS 候选，不表示任何 Linux 环境都已经具备可用的名称解析和组播路径。[候选解析](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/src/candidate.cpp#L139)、[异步解析入口](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/src/impl/peerconnection.cpp#L1190)、[固定版兼容说明](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.6/README.md#compatibility)。

即使车端暂不能解析浏览器的 `.local`，浏览器对车端数值 host 候选发起检查后，ICE 的 peer-reflexive 学习可能建立有效路径；这是可行性推断，必须检查实际选中候选，不能承诺一定成功。[RFC 8445 peer-reflexive 学习](https://www.rfc-editor.org/rfc/rfc8445.html#section-7.3.1.3)。不能将 WebSocket 信令连接的来源 IP 无条件替换进浏览器所有候选；它可能不对应浏览器实际发送 UDP 的网卡或地址。

验收应保存 ICE/PeerConnection 状态、候选类型及选中地址对、DataChannel 打开时间与错误。建连失败时保持停车，明确显示连接失败；不为了研究擅自修改系统 mDNS、驱动、防火墙或浏览器安全策略。

## 5. 切换、关闭与验收要求

以下是本项目的安全设计要求，来源是现有独立门控职责，不是 RTCDataChannel 的自动保证：

- 任意时刻只认一个活动控制通道；协议切换先撤销运动许可并停车，再建立新通道、取得新会话并由用户重新使能。
- `close/error/disconnected/failed`、页面挂起和新鲜度截止均锁停；链路恢复、重新协商或回退到旧 WebSocket 不能自动恢复上一条运动命令。
- 新通道绑定连接代次、会话与递增序号；旧通道回调不能续租、恢复使能或覆盖新通道状态。乱序到达的数据也必须经过同一 Safety 检查。
- 零速/停止消息也可能丢失，不能只靠浏览器“已发送停止”证明车停；Safety 必须在独立周期按过期条件输出零速。显式关闭通知可以加快撤销，但不能替代超时停车。

先离线验证参数、乱序/丢包、过期拒绝、缓冲上限及重连锁停，再用实际 LAN 浏览器比较旧 WebSocket 与 RTC：连接成功率、选中候选、控制最大间隔、授权年龄、积压及停车结果。最后才在现场安全前提下验证实车运动。若仍发生超过 300 毫秒的无线断流，RTC 同样应停车，记录通信验收失败；本文不将换协议、编译成功或本机联通写成 Wi-Fi 已修复。

可借鉴的是把按住运动、松手归零和命令过期停车分开处理。两个官方组件没有定义本项目浏览器的静止会话、前后台或窗口焦点规则，不能由其未提及心跳推断“官方保证静止免心跳”。差速控制器的 0.5 秒默认值也不是本车推荐门限，本轮不替换底盘模型、不引入这两个组件。

本项目 R10 取舍如下，属于本项目设计，尚须对应回归及现场验收：

- **静止就绪**：速度保持零，静止时不靠操纵心跳续许可；开始新的按住操纵仍须当前会话、当前车端挑战及有效序号，不能沿用旧运动消息。
- **运动截止**：保留车端签发后 300 毫秒有效期和独立停车周期；松手归零并建立序号屏障，晚到的松手前运动消息不能再次驱动车轮。正常松手后可再次按住，通信断流不能延长旧指令许可。
- **状态事件**：断开、页面隐藏及传感器故障继续锁停；窗口 `blur` 只在正按住摇杆时触发停车，静止时失去焦点不反复撤销就绪。连接恢复或页面重新显示仍不自动恢复旧运动。

验收应分别覆盖长时间前台静止、静止切焦点、按住时切焦点、松手后乱序到达、运动断流、隐藏/断开与传感器故障；同时检查零输出、重新操纵条件及 300 毫秒截止。采用成熟组件的职责划分不构成本项目认证，也不证明现场无线链路已经修复。

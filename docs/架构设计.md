# 架构约定

## 包职责

| 包 | 当前职责 | 禁止放入 |
|---|---|---|
| `rosmaster_vendor` | 原厂 V3.3.9 Python 库的可复现安装 | ROS 话题、业务代码 |
| `carcar_base` | 串口生命周期、电机指令、板载传感器、轮速里程计 | 地图、Nav2、巡检状态机 |
| `carcar_description` | 机械结构、传感器安装位、静态 TF | 串口访问、导航参数 |
| `carcar_lidar` | RPLIDAR A1 的 Humble 参数、正式启动及独立 RViz 测试入口 | 厂商 SDK、底盘串口、导航算法 |
| `carcar_bringup` | 参数汇总与启动编排 | 算法实现 |
| `carcar_navigation` | SLAM/定位/Nav2 配置 | 厂商驱动、巡检业务 |
| `carcar_algorithms` | 可复用的感知/规划算法 | 任务流程和设备驱动 |
| `carcar_inspection` | 点位巡检、任务状态机、告警/上传等应用逻辑 | 底盘协议实现 |

## ROS 接口

`carcar_base` 对上层只暴露 ROS 标准消息：

- 订阅 `/cmd_vel` (`geometry_msgs/Twist`)
- 发布 `/imu/data_raw` (`sensor_msgs/Imu`)
- 发布 `/wheel/odometry` (`nav_msgs/Odometry`)
- 发布 `/battery_state` (`sensor_msgs/BatteryState`)
- 发布 `/wheel/encoders` (`std_msgs/Int32MultiArray`，顺序 M1～M4)
- 发布 `/diagnostics` (`diagnostic_msgs/DiagnosticArray`)

底盘节点默认不发布 `odom -> base_footprint`，避免与后续 `robot_localization` 重复发布 TF。当前里程计可直接供调试使用；正式导航阶段建议融合轮速与 IMU，融合节点唯一发布 `odom -> base_footprint`。

## TF 目标树

```text
map                       SLAM 或 AMCL 发布
└── odom                  状态估计发布
    └── base_footprint
        └── base_link     robot_state_publisher 发布
            ├── imu_link
            ├── laser_frame
            └── camera_link
```

## 后续实施顺序

1. 确认串口、车型和轮向，标定速度与 IMU 轴向。
2. 测量车体和传感器安装尺寸，更新 Xacro。
3. 引入 `robot_localization`，校准轮速里程计与 IMU 协方差。
4. 按 `LIDAR-001` 完成 Humble 雷达数据、RViz 和 TF 实测后，使用 `slam_toolbox` 建图。
5. 调整 Nav2 footprint、速度、代价地图和控制器。
6. 在 `carcar_algorithms` 中加入复用算法，在 `carcar_inspection` 中实现巡检流程。

# D435 图像显示比例与配准依据

日期：2026-10-08。范围：显示和配准的离线源码核对；不作为实机标定或导航验收结论。当前操作入口仍为[操作手册](../操作手册.md)，当前状态以[测试记录](../测试记录.md)和[硬件台账](../硬件台账.md)为准。

## 1. 本次结论与证据边界

用户现场反馈：三个 RViz 图像的比例与真实画面不匹配，会造成误解；只看覆盖范围较广的深度画面时，物体与体素基本匹配，STVL 使用效果较理想。这支持先纠正显示参照关系，不能据此宣布所有 STVL 动态、安全和导航验收通过，也不能直接把不匹配归因于体素算法。

离线检查了 `image_reference.hpp`、`reference_camera_info.hpp`、`reference_camera_info.cpp`、`image_reference_preview.cpp`、`image_reference_alignment.launch.xml`、两个 RGB 候选配置及三图 RViz 候选。现有 RGB、原深度参照均为等比例缩小；三个独立 Image 窗格的布局没有固定为同一有效绘制尺寸。**窗格大小、图像宽高比、镜头视场、配准目标网格是四种不同问题，应分别验证。**

本轮续读主机布局：主代理报告原三个 Image 实际渲染区域分别为 677×212、677×80、677×146；用户已明确指出窗口大小不同。当前处理优先使用 RViz 原生窗口布局持久化，不需要为窗口大小问题新增图像处理算法。下文光学与配准说明用于避免把仍然存在的视场差异误当作修复失败。

## 3. RViz 自带的保比例机制

**源码已证实：** `ImageDisplay::update()` 比较纹理宽高比和显示窗格宽高比，再设置图像矩形边界。窗口变化会改变缩放和黑边，不会直接把原图横纵分别拉满。该插件没有用 CameraInfo 把两路不同镜头变成同一视场。[11.2.29 ImageDisplay 源码](https://github.com/ros2/rviz/blob/11.2.29/rviz_default_plugins/src/rviz_default_plugins/displays/image/image_display.cpp#L146-L169)

**本项目推断：** 只把三张 320×240 图放入大小不同的窗格，仍可能使同一物体在屏幕上看起来大小不同；让窗格一样大也不能消除 RGB 与深度的视场差异。需要看最终 Ubuntu 桌面有效图像边界，不能拿未经确认的示意图或代理端图片代替现场画面。

### 3.1 官方窗口布局持久化路径

`VisualizationFrame::load()` 先加载显示组件与 Panels，再加载 Window Geometry；后者先设主窗口宽高，再从 `QMainWindow State` 的十六进制字符串恢复 dock 布局。保存调用 Qt 的 `saveState().toHex()`。只设整体 Width/Height 不会定义三窗同排等大。[11.2.29 VisualizationFrame 加载/保存](https://github.com/ros2/rviz/blob/11.2.29/rviz_common/src/rviz_common/visualization_frame.cpp#L760-L833)

Image 的关联窗由 `Display::setAssociatedWidget()` 创建；dock 的 objectName 等于显示组件 Name，显示改名时同步改变。保存的状态必须对应当前三个名字；不能保留旧名字的状态后随意改 Name。默认 addPane 是左侧区域、floating=true；没有恢复状态时，不保证所需底部同排布局。[Display 关联窗](https://github.com/ros2/rviz/blob/11.2.29/rviz_common/src/rviz_common/display.cpp#L368-L397)、[Display 改名](https://github.com/ros2/rviz/blob/11.2.29/rviz_common/src/rviz_common/display.cpp#L442-L451)、[dock 创建](https://github.com/ros2/rviz/blob/11.2.29/rviz_common/src/rviz_common/visualization_frame.cpp#L1212-L1237)、[接口默认值](https://github.com/ros2/rviz/blob/11.2.29/rviz_common/include/rviz_common/window_manager_interface.hpp#L61-L67)

推荐以 Qt 原生底部 dock、水平分隔、等宽 resizeDocks 生成可恢复状态，再写入新增 .rviz 候选；避免手工编造 Qt 状态字节。Qt 按最小/最大尺寸和可用区域分配空间，所以最终需要恢复后实读三块 RenderPanel 的尺寸，允许像素取整的 1～2 px 差异；随后看每幅 4:3 图像有效区域是否一致。这个修改复用成熟框架、无需增加执行逻辑，也不改变深度或体素数据。[Qt 5.15 QMainWindow 布局接口](https://doc.qt.io/archives/qt-5.15/qmainwindow.html#resizeDocks)、[saveState 名称要求](https://doc.qt.io/archives/qt-5.15/qmainwindow.html#saveState)

**Camera 叠加的限制：** `CameraDisplay` 用 CameraInfo 的 P、width、height 和图像 optical frame 建立三维投影；它在该版本直接读这些字段，没有通过 image_geometry 解释 binning 或 ROI。若用当前 binning=2 的参照内参直接配 320×240 纹理做 Camera 显示，不能保证符合缩小后的投影；应另提供宽高、K/P 均按缩放统一且 binning=0 的显示专用内参，并验证 TF。[11.2.29 CameraDisplay 源码](https://github.com/ros2/rviz/blob/11.2.29/rviz_default_plugins/src/rviz_default_plugins/displays/camera/camera_display.cpp#L486-L591)

## 4. ROS 配准怎样解释缩放

**源码已证实：** RegisterNode 3.0.9 的输入包括深度 Image、深度 CameraInfo、目标 RGB CameraInfo；以 optical frame 的 TF 转换三维坐标后投影到 RGB 的 P 网格，输出尺寸来自目标 `reducedResolution()`，输出内参复制目标 RGB 内参。`fill_upsampling_holes=false` 投影有效深度像素并保留较近深度；true 使用像素覆盖区填入目标网格。后者解决采样产生的空洞，不能恢复原相机没有看到的表面。[3.0.9 RegisterNode 源码](https://github.com/ros-perception/image_pipeline/blob/3.0.9/depth_image_proc/src/register.cpp#L145-L294)

`image_geometry` 3.2.1 将 binning=0 解释为 1，K/P 的焦距和主点按 binning 除算，目标分辨率按 ROI 和 binning 减小。因此，640×480 原内参保持不动、设置 binning_x=binning_y=2，可以得到正确的 320×240 目标模型；不能再把 K/P 除以 2，否则二次缩放。[3.2.1 PinholeCameraModel 源码](https://github.com/ros-perception/vision_opencv/blob/3.2.1/image_geometry/src/pinhole_camera_model.cpp#L91-L222)

**仍待核对：** 当前 RGB 参照取 `color/image_raw`，ROS RegisterNode 投影目标为校正图像模型 P。若本机 RGB D 非零、R/P 与 raw 模型不一致，需要先生成 RGB 校正参照，再与配准深度对比；不能把 raw 边缘误差诊断为体素误差。CameraInfo 对 K、D、R、P 的原始/校正图像区别有明确约定。[固定版本 CameraInfo 定义](https://github.com/ros2/common_interfaces/blob/4.8.0/sensor_msgs/msg/CameraInfo.msg)

## 5. 为什么原深度不能与 RGB 直接等大比较

**厂商规格：** 产品页写 D435 深度 87°×58°、RGB 69°×42°；数据手册另区分深度 HD（16:9）87°×58°和 VGA（4:3）75°×62°。当前 640×480 属于 VGA，不能沿用 HD 宣传值解释画面。型号存在镜头差异，最终应从本机当前流内参计算覆盖角。[D435 规格](https://www.realsenseai.com/products/stereo-depth-camera-d435/)、[337029-017 第 69 页表 4-1](https://realsenseai.com/wp-content/uploads/2024/10/Intel-RealSense-D400-Series-Datasheet-October-2024.pdf#page=69)

**项目已有证据：** 2026-10-07 读取深度 fx=fy=385.14886475、640×480，角覆盖约水平 79°、垂直 64°。这是读取内参推算，不能当作绝对光学校准验收。[此前核对记录](2026-10-07-D435安装角与STVL响应调研.md)

**厂商示例已证实：** 配准是将一个视点映射到另一个视点得到的合成流，会改变采样，也存在遮挡；输出无有效值的区域并非自动代表“没有障碍”。SDK 实现使用深度、两路内外参和目标尺寸进行重投影，原图等宽缩小或中心裁剪不能替代。[2.58.4 rs-align 示例](https://github.com/IntelRealSense/librealsense/blob/v2.58.4/examples/align/rs-align.cpp#L5-L18)、[2.58.4 align 实现](https://github.com/IntelRealSense/librealsense/blob/v2.58.4/src/proc/align.cpp)

## 6. 可执行的下一步与验收指标

1. **优先保持当前深度/STVL 链路。** 先交付新增 .rviz 布局候选，将三个 Image 窗格保存为底部同排、同高、等宽；RGB 与“投影到 RGB 网格的深度”作为同网格对照，原宽视场深度保留且明确标注“深度原视场”。收益是避免独立窗格缩放造成误判，代价是原视场图与 RGB 图仍不能逐像素比较；不能强行拉伸让它们看起来一样。
2. **像素配准只比较同一目标网格。** 固定静止场景，在两个不同距离的箱体边界上比较 RGB/配准深度像素；记录实际尺寸、时间戳差、内参和 TF，以及边缘误差的中位数/P95。遮挡边缘、原深度为 0 和 RGB 视场外区域单独说明；误差阈值待基线实测，不能预设“已经准确”。
3. **若需要三维体素直接压在相机画面上，优先评估 RViz Camera。** 原插件已有 TF 与内参投影，减少维护代码；代价是缩小内参必须扁平化、图像必须匹配校正模型、Wi-Fi 和渲染负载需重验。当前阶段先修正二维参照呈现，避免一次叠加显示和三维投影问题。
4. **确认不会影响避障输入。** 相机原深度尺寸、帧率、过滤输入话题和 STVL 标/清障参数应与当前候选保持一致；记录画面加入前后的点云最大间隔、最大年龄、健康异常数。只有实际 Ubuntu 主机 RViz 屏幕经现场确认，才写“显示比例实机确认”。

本轮不新增执行脚本、不修改相机 SDK 配置、不改变 STVL 参数，不删除任何失败记录。以上为官方资料和仓库逻辑的离线核对；当前图像、内参和桌面布局仍需在同一运行窗口实读验证。

## 7. 同日补充修订：视场解释接受与已保存内参复核

用户已接受原生深度视场宽于RGB属于正常镜头差异，要求同步文档。当前读图与操作说明集中在[手册31.11](../操作手册.md#3111-深度配准到-rgb-的显示参照nav-016-r2)，本节保留来源与推算依据，不复制操作命令。

本次重新核对[厂商D435规格页](https://www.realsenseai.com/products/stereo-depth-camera-d435/)，深度87°×58°、RGB69°×42°为型号/HD参考，仍须区分数据手册中的流模式。固定SDK版本[librealsense 2.58.4 rs-align](https://github.com/realsenseai/librealsense/blob/v2.58.4/examples/align/rs-align.cpp)说明配准使用目标视点生成合成流，无法消除原始两镜头的不同视点、采样与遮挡；本项目继续复用ROS RegisterNode，不因本次解释改变运行算法。

复核的是已保存数据，并非新实机采样：深度 `log/stvl_image_reference_20261007_01/depth_intrinsics_rgb_enabled.yaml` 为640×480、fx=fy=385.14886474609375；RGB `log/stvl_display_proportion_20261008_01/rgb_camera_info.yaml` 为640×480、fx=607.5086059570312、fy=606.4273071289062，D全0、R单位矩阵、P与K一致。因此第4节所述raw/rect模型不一致在该保存帧没有支持证据；改变流模式后需重新核对，仍不能据此宣称像素配准误差已验收。

按 `2×atan(尺寸/(2×焦距))` 复算，深度约79.44°×63.86°、RGB约55.56°×43.18°；这是针孔模型覆盖角估算，不是绝对光学校准。导航保留原生深度点云经现有过滤后的宽视场观测，RGB配准图仅供显示/认物；当前实验层为STVL 2.3.4，原生VoxelLayer是保留的历史对照。视场差异本身不构成安装TF错误证据，也不排除独立的外参问题。本次仅修订文档，不新增健康、低障碍或移动验收结论，历史失败与原始结果保持。

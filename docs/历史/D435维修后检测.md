# D435 维修后检测（CAM-001）

2026-09-07 故障暂停：用户运行 realsense-viewer 后整机黑屏重启。以下 Viewer 与出帧
命令暂缓执行，先查重启原因；不以无图形脚本保证不会再次重启。已发现重启前后持续
UVC GET_CUR -32 错误，原因尚未确定。USB 当前仍为 5000M。旧命令保留用于后续恢复。

补充日志显示视频 completion handler 多次返回 `-71`，但没有 kernel panic、GPU fault、
过温或正常关机记录。先把 D435 接到另一台电脑的 USB 3 口，以厂家 Viewer 按“仅彩色、
仅深度、彩色+深度”隔离测试；Jetson 上的所有视频流命令继续暂停。另一台电脑通过后，
已确认 Jetson 当时使用原装电源适配器；再决定是否用不同端口或独立供电 USB Hub 恢复
本页后面的低帧率命令。不要在当前状态升级
相机固件或反复热复位设备，以免把维修状态、固件和供电问题混到一起。

2026-09-07 外部主机复测通过：同一 D435 在另一台电脑以 USB 3.2 同时输出 RGB、左右红外
和深度，`640×480 @ 30`，实际约 `31.4 FPS`，超时为 0。相机基本功能不再列为主要嫌疑；
本页后续 Jetson 测试改为不同物理端口或独立供电 USB 3 Hub 下的单流低负载短测，Viewer
继续暂停。深度中心 `2.455 m` 尚无标尺真值，只作画面记录。

2026-09-07 Jetson 低负载复测：更换物理口后，单彩色、单深度及彩色+深度均以
`640×480 @ 6` 连续运行 10 秒并通过脚本判定，超时均为 0，未再次重启。联合流收到
彩色/深度各 56 个唯一帧，约 5.52 FPS；中央有效深度均值约 88.59%，距离中位数约
2.419 m。与此同时，内核仍约每 6 秒出现两个视频接口的 `completion handler -71`，并
伴随 `GET_CUR -32`。相机空闲、无进程占用且 USB runtime suspended 时错误仍出现，故
Jetson 侧只记为“低负载出帧通过、内核链路未验收”，暂不进入 15 FPS、长测或 Viewer。

2026-09-07。目的：检查维修后的设备枚举、彩色、深度和联合出帧。使用本机官方
`pyrealsense2 2.55.1.6486`（SDK v2.55.1，Apache-2.0），参考
https://github.com/realsenseai/librealsense/tree/v2.55.1/wrappers/python/examples 。
本项目独立实现统计与错误报告，不复制厂家代码；直接 SDK 检测用于先排除 ROS 配置影响。

前提：关闭 RealSense Viewer 和相机 ROS 节点，一个进程独占相机。车辆静止，镜头前
0.5～1 m 放不反光纸箱或有纹理墙面，正常室内光照。脚本不连接底板串口或控制电机，
不更新固件、不复位设备、不写相机标定。最初 USB 类型为 2.1；换线后已确认同一相机为
USB 3.2、5000M。原 USB 2.1 结果作为历史保留，不再代表当前连接状态。

观察 JSON：`unique_frames` 应持续增加，`received_fps` 接近请求帧率，`timeouts=0`。

应大致对应纸箱距离；它不是精确单点标定。有效比例低时换普通纸箱/距离重新测。
`color_sample_range_mean` 只检查抽样亮度跨度，不证明颜色正确或画面未冻结。
设备编号更新也不能排除画面内容冻结，必须人工移动目标复核。

## Jetson USB 自动挂起隔离检查

当前 Jetson 为 L4T R36.4.7、内核 `5.15.148-tegra`；系统 `uvcvideo` 模块版本为 1.1.1，
模块信息没有 `realsense` 标记。官方 Jetson 安装指南说明原生 UVC 用于生产环境时可能
需要应用 RealSense 的 L4T 内核模块补丁。补丁会构建并替换内核模块，风险高于参数隔离，
所以先执行下面的自动挂起 A/B 测试，不直接安装补丁。参考来源：
https://github.com/realsenseai/librealsense/blob/master/doc/installation_jetson.md 。

本机 SDK 报相机序列号 `213222078719`，USB sysfs 描述符报 `214423022357`。脚本优先按
传入序列号匹配；若不匹配但系统中只有一台 USB ID `8086:0b07` 的 D435，则打印警告后
使用该唯一设备。发现多台时拒绝猜测。序列号差异原因待确认，不把它单独判成硬件故障。

测试前关闭所有相机程序。脚本阶段 A 保持当前 `auto`，阶段 B 临时改为 `on`，各观察
20 秒的内核 `-32/-71` 计数；退出、报错或 Ctrl+C 都会尝试恢复原值。它不启动视频流，
也不更新固件。执行时 sudo 只用于写当前相机的 sysfs 电源属性：

首轮现场执行虽然成功恢复 `auto`，但零计数因旧脚本时间戳不兼容和 `-71` 匹配错误而
无效。当前版本已修订，`journalctl` 读取失败会直接报告错误；须以下面命令重新执行。

修订版现场结果：阶段 A（`auto`）为 `GET_CUR -32=30、completion -71=6`，阶段 B
（`on`）仍为 `30/6`；最后已恢复 `auto`，未发生重启。因此不采用永久关闭 USB 自动
挂起的方案。该结果把后续重点转到原生 `uvcvideo` 与 D435 的兼容链路；优先规划隔离的
RSUSB 用户态后端对照，验证后再决定是否替换 Jetson UVC 内核模块。

```bash
cd /home/jetson/luhao/my_nav_carcar
conda deactivate 2>/dev/null || true
source /opt/ros/humble/setup.bash
bash -n scripts/check_d435_usb_autosuspend.sh
pgrep -af '[c]heck_d435.py|[r]ealsense-viewer|[r]ealsense2_camera' || true
fuser -v /dev/video* 2>/dev/null || true
OBSERVE_SECONDS=20 bash scripts/check_d435_usb_autosuspend.sh 213222078719 | \
  tee /tmp/carcar_d435_autosuspend_ab.log
```

停止与恢复：正常等待脚本结束；需要中断时按一次 Ctrl+C，随后核对已恢复为原值。若终端
或机器在恢复前异常退出，重新执行最后两行手工恢复：

```bash
cd /home/jetson/luhao/my_nav_carcar
D435_USB_PATH="$(dirname "$(grep -l '^214423022357$' /sys/bus/usb/devices/*/serial | head -n 1)")"
printf 'auto\n' | sudo tee "$D435_USB_PATH/power/control"
cat "$D435_USB_PATH/power/control" "$D435_USB_PATH/power/runtime_status"
```

预期判读：若阶段 B 的 `-71` 明显归零而阶段 A 持续出现，自动挂起是直接触发条件，可再
评估只对该相机设置 udev 电源规则；若两阶段都出现，优先转向 RealSense L4T 专用 UVC
模块或独立供电 USB 3 Hub。两种情况均不据此判定相机硬件再次损坏。

## CAM-002：低负载图形窗口检查

用途：在厂家 Viewer 曾导致 Jetson 黑屏重启的前提下，以较低负载人工检查彩色画面、
伪彩深度、中心 60×60 像素区域的深度中位数、整幅有效深度比例和实际帧率。默认只启用
RGB 与 Depth `640×480 @ 6 FPS`，不启用左右红外、点云、深度对齐或录制；只读相机，
不修改固件、标定、内核或 USB 电源策略。

运行前关闭 Viewer、ROS 相机节点和其他 D435 脚本。相机实物为倒装，脚本
默认对诊断窗口旋转 180°（`--rotate 180`）；这只影响显示，不改原始帧、
标定或 RealSense optical frame。窗口左侧为 RGB，右侧为 0～4 m
伪彩深度；把普通纸箱依次放在约 0.5 m、1 m 处，查看白框中心读数是否随之变化。窗口
出现花屏、冻结、连续超时或系统明显卡顿时，按 Q/Esc；键盘无响应则在终端 Ctrl+C，
仍无响应时拔掉 D435 USB：

```bash
cd /home/jetson/luhao/my_nav_carcar
conda deactivate 2>/dev/null || true
source /opt/ros/humble/setup.bash
/usr/bin/python3 -m py_compile scripts/view_d435_safe.py
pgrep -af '[r]ealsense-viewer|[r]ealsense2_camera|[c]heck_d435.py|[v]iew_d435_safe.py' || true
fuser -v /dev/video* 2>/dev/null || true
/usr/bin/python3 scripts/view_d435_safe.py --serial 213222078719 --fps 6 --max-depth 4.0 --rotate 180
```

预期：两幅画面持续更新；移动手或纸箱时 RGB 和深度同时变化；中心白框对准普通目标时
显示有限距离，实测 FPS 接近 6，画面不出现固定条纹、半幅缺失或长时间冻结。关闭窗口
后脚本会停止 pipeline。恢复检查：

```bash
cd /home/jetson/luhao/my_nav_carcar
pgrep -af '[v]iew_d435_safe.py|[r]ealsense-viewer|[r]ealsense2_camera' || true
fuser -v /dev/video* 2>/dev/null || true
```

实际结果：2026-09-07，修订后窗口连续运行至少 2382 组画面，稳定约
`6.03 FPS`。用户确认 RGB 与伪彩深度无冻结、条纹、半幅丢失等异常，
目标移入中心区域时距离由约 2 m 变为约 0.48～0.58 m，随后正常恢复。
脚本由 Ctrl+C 停止，pipeline 关闭且无残留进程。CAM-002 判定为“低负载画面通过”。
这不等于绝对测距精度或高帧率长时稳定性通过；内核 `-71/-32` 依然保留为已知问题。

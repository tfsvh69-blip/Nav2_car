按住摇杆时网页每 50ms 重复当前方向，松手立即发零。车上从最后一次收到推杆起保持 1 秒，到点只把速度归零，不撤使能；下一条新命令可以直接继续。挑战不再用来续租。序号仍丢掉松手之前排队的旧方向。会话未就绪仍是 0.30 秒，雷达和里程计仍是 0.50 秒，这些失效会撤使能。断联后慢档最多再走约 5cm，快档约 18cm。这不是物理刹停或硬实时保证。摇杆支持前后/转向组合，有限值、归一化输入和档位上限在车端检查，不提供横移。松手归零并保留使能，使用递增序号拒绝松手前的排队请求；停车锁定、换档、后台、断联、故障、保存和重启后重新使能。视频默认按需开启，不参与建图或常驻入口运动授权；旧严格模式`require_video=true`仍检查源帧与浏览器绘制帧。雷达、里程计、网关与短授权检查保留。所有运动经专用`/mapping/cmd_vel`，底盘0.30秒软件超时保留；Jetson卡死/控制板独立停车仍需实机验证。

任务使用固定argv与独立进程组，不执行网页提供的shell。结束先停车并保存，成功后退出本工具底盘/雷达/SLAM/门控及可选相机，网页回待命；保存失败锁停等待重试，不自动退出。重启提示未保存损失，有本次成功版本时从最近版本续建，仍须人工对齐。不自动启动/重启硬件，不杀未知串口进程。用户服务沿用当前GDM自动登录，系统设置不改，真正重启后入口与平板效果仍须现场验收。

前端未使能时不发送无用操纵心跳；使能后每条新挑战最多一条周期回应，心跳与运动共用这一规则，定时器不重发旧挑战；按压更新本地意图，随下次新挑战发送，松手/停车立即发送。控制状态按签发编号拒绝乱序，门控重启需按签发代次区分；地图/预览路径保持R8分流。网页显示实际连接通道，在辅助区可选择旧WebSocket作对照；新通道不可用时锁停并回退，不改变停车期限。

依赖为官方`libdatachannel v0.24.6`固定提交、仅数据通道及其3个固定子模块；首次构建可联网取源码，运行不访问外部STUN/TURN。第三方原许可证随安装保留，自有代码保持Apache-2.0；构建可关闭`MAPPING_ENABLE_WEBRTC`，旧通道仍可独立构建。来源、许可证和适用边界见[专项调研](../../docs/archive/2026-10-15-网页建图WebRTC控制通道调研.md)，完整操作统一手册33.14，实际结果见测试记录R9。无线中断、浏览器挂起或总往返耗尽300ms仍须停车，换协议不等于现场已通过。

NAV-017-R10（2026-10-15，当前规则）：用户指出目标仅网页遥控建图且停止过多。使能代表等待下一次按压的就绪状态，静止及松手后不靠操纵心跳续期；首次使能等待状态返回也不再触发300ms静止心跳锁停。新门控报告`idle_heartbeat_required=false`，新网页停止空闲操纵心跳；旧门控缺此字段时仍沿用旧网页回应，旧网页连接新门控仍可发送兼容心跳。兼容心跳期限只作诊断，不触发运动、不延长运动期限。窗口失焦只在仍按住摇杆时停车，页面隐藏/关闭/断开与关键传感器/会话故障仍锁停；运动仍必须在车端签发后300ms内更新，松手序号屏障和恢复不重放旧动作不变。来源与取舍见专项调研R10段，操作/恢复和验证统一手册33.15与测试记录R10；软件零命令不等于实物停止反馈。

NAV-017-R14（2026-10-19）：现场使能后出现「网页请求停车: rtc_fallback / rtc_cancelled」，使能状态来回跳；推杆后另出现「操纵授权超时」。原因是 WebRTC 接通、回退和短暂断开都会发停车，运动包又只走不可靠数据通道。现在页面默认使用 WebSocket。通道接通或回退不再撤销使能；若仍选择 WebRTC，同一条运动同时送一份可靠副本，车端只接受带 backup 的副本，切换前排队的旧 TCP 运动继续丢弃。300ms 仍从签发时刻计算，副本迟到不能续租。页面版本 `20261019-r14`。刷新网页即可加载；网关进程要等本次建图结束后重载，才不再因数据通道状态自行停车。操作见手册 33.18。
